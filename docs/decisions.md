# Decisions

Append new entries; never silently change old ones. Format: `D<n> (date): decision. Why.`

**D1 (2026-10-18): Rust only, native egui/eframe on wgpu.** No Tauri, Electron, webview or JavaScript UI. One language, one binary, and the engine stays shared with the CLI and MCP.

**D2 (2026-10-18): Product is "Inbetween"; the CLI binary is `ib`.** Crates are `inbetween-*`, the desktop binary is `inbetween`, project files are `.inbetween` and dot sets `.inbetweendots`. `ib` is short to type for a tool used constantly from a shell.

**D3 (2026-10-18): Layering enforced by `cargo xtask layers`.** A crate may depend only on strictly lower layers, and UI crates are banned below L6. Registry lives in `xtask/src/layers.rs`. It keeps the engine reusable headless and wasm-clean.

**D4 (2026-10-18): Panicking forms banned in non-test code.** Crate-level `deny` attributes plus `clippy.toml` test exceptions, and `unsafe_code = "forbid"` workspace-wide. Hostile input must produce errors, not crashes.

**D5 (2026-10-18): Licences restricted to permissive ones.** `deny.toml` allows MIT, Apache-2.0, BSD, Zlib, ISC (plus Unicode and CC0 for data crates).

**D6 (2026-10-18): `xtask` uses `serde` and `serde_json` to read `cargo metadata`.** Both are MIT/Apache-2.0 and avoid hand-parsing manifests.

**D7 (2026-10-18): Delaunay via `spade` (MIT/Apache-2.0), geometry in `f64`.** Exact predicates make the triangulation robust to collinear and near-degenerate dots, so we do not write our own. Duplicate dots are rejected with `DuplicateDot { first, second }` rather than silently merged, so paired dot sets keep their indices. Collinear dots and fewer than three dots are accepted because the four frame corners always give the mesh area. A dot on a frame corner replaces that corner. Dots outside the frame are allowed; the mesh then covers their convex hull, which contains the frame. `MAX_DOTS` is 100,000.

**D8 (2026-10-18): Working pixels are premultiplied f32 holding sRGB-encoded values (no linearisation).** The 8-bit sRGB boundary then only divides or multiplies by 255 and premultiplies, so every non-transparent 8-bit pixel round-trips exactly (tested for all 255 alpha x 256 colour values), and t=0 / t=1 frames match the sources. Dissolves therefore blend in display space, as users of image tools expect; a linear-light option can be added later by converting at the same boundary. Fully transparent pixels normalise to `[0,0,0,0]` on output.

**D9 (2026-10-18): Image coordinates put pixel centres at +0.5; sampling is bilinear with edge clamp on premultiplied values.** Premultiplied interpolation is alpha-correct (no dark fringes next to transparency). NaN and infinite positions are clamped, never propagated.

**D10 (2026-10-18): PNG and JPEG via the `image` crate with only the `png` and `jpeg` features** (MIT/Apache-2.0). Decode checks the header against limits first (side at most 32,768, at most 100,000,000 pixels). 16-bit PNGs reduce to 8-bit. JPEG output has no alpha, so it composites over white. The `codecs` crate has no workspace dependencies; file helpers are `cfg(not(wasm32))`.

**D11 (2026-10-18): `cargo xtask wasm` checks every registered L0 to L5 crate for `wasm32-unknown-unknown`,** and runs in `xtask ci` and GitHub Actions.

**D12 (2026-10-18): Dot coordinates live in output-frame pixels** (y down, origin top-left). Sources of other sizes are fitted to the output first, so dots are placed on the fitted images. Fit modes: `stretch` (default; each axis scaled independently), `contain` (uniform, transparent bars) and `cover` (uniform, cropped). Only `contain` reads transparent outside the source; the others repeat edge pixels. Same-size sources fit as an exact identity.

**D13 (2026-10-18): One shared mesh, built from Image 1's dots; the last frame uses a mesh from Image 2's dots.** The default policy (`frame0`) triangulates once and reuses the connectivity, interpolating vertex positions. When dots move far the shared mesh can fold in the middle of the sequence, but frame 0 is Image 1 and the last frame is Image 2 exactly because the end frames use their own meshes. `per_frame` re-triangulates each interpolated frame, falling back to the shared mesh on frames where two dots coincide. Duplicate dots on either image are an error that names the image.

**D14 (2026-10-18): Frame time is `i / (n - 1)`; a one-frame sequence is Image 1.** `Point::lerp` is now written `a*(1-t) + b*t` so it returns `a` at t=0 and `b` at t=1 bit-exactly.

**D15 (2026-10-18): Deterministic parallel rendering.** Each mesh triangle renders into its own buffer (rayon `par_iter().collect()` keeps order); buffers merge sequentially in triangle order, so overlapping or shared-edge pixels resolve the same way on any thread count. Pixel centres count as inside a triangle with `1e-9` slack so shared edges leave no gaps; any pixel still unclaimed (folded meshes) is sampled unwarped. If the inverse map for a layer is singular, that layer is sampled unwarped in that triangle.

**D16 (2026-10-18): File formats are JSON in a named, versioned envelope.** `.inbetween` is `{"format":"inbetween-project","version":1,"project":{...}}` and `.inbetweendots` is `{"format":"inbetween-dots","version":1,"pairs":[...]}`. JSON (via `serde_json`, MIT/Apache-2.0) keeps files diffable and writable by agents. The marker is checked before the body so a wrong or newer file gets a clear message. Reading ignores unknown fields and defaults missing ones, so adding an optional field never needs a version bump; a higher version than the build knows is refused (`NewerVersion`), never half-read. A UTF-8 BOM is tolerated.

**D17 (2026-10-18): Reading is bounded and writing is safe.** Files over 64 MiB, projects over 10,000 sequences, and any model-limit breach (frames, dots, output size, non-finite numbers) are errors. Image paths must be relative: absolute paths, drive letters and UNC paths are rejected on read and write; `..` is allowed so a project can sit beside an `images` folder. `make_relative` builds such paths lexically. Writes go to a temporary file in the same directory and are renamed over the target, so a full disk or crash leaves the old file intact; an invalid project is never written.

**D18 (2026-10-18): Parser robustness is tested twice.** `crates/format/tests/robustness.rs` runs deterministic mutation fuzzing on stable Rust in every `cargo test` (all truncations, all single-byte changes, 60,000 mutated seeds, random bytes, depth bombs), asserting no panic and write/read stability. `fuzz/` holds libFuzzer targets (`project`, `dots`) run by `.github/workflows/fuzz.yml`: 3 minutes per target on pull requests touching `format`, `doc`, `geom` or `fuzz`, 15 minutes weekly. The fuzz crate sits outside the workspace because `libfuzzer-sys` carries the (permissive) NCSA licence, which `deny.toml` does not allow.

**D19 (2026-10-18): Commands are data plus two function pointers.** A `CommandSpec` has an id, label, menu path, shortcut, description, a static parameter schema (`ParamSpec`: name, kind, required, range, default), an `enabled(&Session)` check with a reason, and `run(&mut Session, &Params)`. `Registry::run` validates parameters against the schema before `run` is reached: the value must be an object, unknown keys are rejected (the error lists the valid ones), types and ranges are checked, strings are capped at 4,096 bytes and may not contain NUL. Commands therefore never see raw JSON. `Registry::run_caught` additionally turns a panic into `CommandError::Internal` for shells that must keep going; tests use `run` so a panic stays visible. Commands live in `<area>_cmds.rs` modules with a `specs()` function. File-touching commands are compiled out on wasm32 (a platform service will replace them).

**D20 (2026-10-18): Image paths resolve against the project file's folder,** are re-checked as relative on every load, and loaded images are cached per `Session` keyed by full path with a (modified time, length) stamp, so a rendered sequence reads each source once and an edited file reloads. `export.sequence` numbers frames from 1 (`frame_0001.png`) and its `prefix` may not contain path separators. `sequence.length` accepts 2 to 999, matching the spec (hold frames arrive in M9); the model itself still allows 1 to 100,000.

**D21 (2026-10-18): Two bugs the M5 tests found, fixed at the source.** (1) serde_json parses floats one bit off unless its `float_roundtrip` feature is on, so dot positions drifted across save and load; the feature is now enabled and a 20,000-pair bit-exact test guards it. (2) Opening a Windows device name such as `CON` blocked forever; `read_file`, `read_project` and `read_dots` now refuse anything that is not a regular file.

**D22 (2026-10-18): The demo pair is generated, not photographic.** `testkit::demo` draws a sun face and a boxy moon face from formulas and returns matching dot pairs; `demo/` holds the rendered PNGs and project, and a test fails if they drift from the generator. No third-party assets, so no `ATTRIBUTION.md` row is needed.

**D23 (2026-10-18): Performance baseline and renderer structure.** `cargo xtask perf` runs `crates/render-cpu/examples/perf.rs` in release mode on a fixed 1080p, 1,000-dot scene at 4 threads, with a 100 ms budget (see `docs/perf.md`). The renderer shades 16-row bands in parallel: each band first records which triangle owns each pixel centre (later triangles win, as before), then colours its pixels. This removed the serial merge, halved the 4-thread time (52 to 28 ms) and made scaling near-linear, with a bit-identical checksum to the previous renderer. Per-triangle setup (bounds and inverse affine maps) still runs in parallel per triangle.

**D24 (2026-10-18): The GPU renderer draws the CPU's plan; tolerance versus the oracle is stated and tested.** `render-gpu` reuses `morph::Planner`, so the mesh and dissolve weight are the oracle's. Per triangle it builds three vertices carrying the output position and the matching position on each source (the oracle's inverse affine map, then the fit, evaluated on the CPU in f64). The GPU interpolates those linearly, which is exact for an affine map, and the fragment shader does the oracle's bilinear, edge-clamped, premultiplied sampling on `Rgba32Float` textures with `textureLoad` (no hardware filtering, so the maths matches). A full-frame unwarped quad is drawn first (the oracle's fallback for unclaimed pixels) and triangles then draw in plan order with no depth test, so later triangles overwrite earlier ones as in the oracle. Tolerances, in premultiplied channels (0.01 is about 2.5 of 255 levels), checked on 14 scenes in `crates/render-gpu/tests/matches_cpu.rs`: ordinary meshes must stay within max 0.01 and mean 5e-4 (observed: max 0.004, mean 7e-5, from GPU vertex snapping to a sub-pixel grid); folded meshes, slivers and the 1080p perf scene may have isolated pixels whose centre sits almost on a shared edge and is claimed by a different triangle, so they get max 0.5, at most 0.3% of pixels over 0.01, and mean 1e-3 (observed on the 1080p scene: 1 pixel in 2 million, mean 2.6e-5). Results are not bit-identical across GPUs or drivers; the CPU renderer stays the deterministic reference and is never adjusted to match the GPU.

**D25 (2026-10-18): Layer checks and licence checks for the GPU stack.** `xtask layers` skips the layer-order rule for dev-dependencies (they never ship, and GPU-versus-CPU tests need both renderers) but still bans UI crates below L6 for every dependency kind. `cargo deny check` now passes on the full tree (wgpu 24, naga, ash, windows crates, rayon, clap, image): licences, sources and bans are clean (`allow-wildcard-paths` for our own unpublished path dependencies). One advisory is ignored with a recorded reason: RUSTSEC-2024-0436 (`paste` is unmaintained), a build-time macro pulled in by wgpu's Metal backend. `cargo deny` had never run before this milestone.

**D26 (2026-10-18): CI runs the GPU tests on Linux against lavapipe (software Vulkan);** `INBETWEEN_REQUIRE_GPU=1` turns "no adapter" into a failure there. On Windows and macOS runners, and on any machine without a GPU, the tests print SKIP and pass. Source and output images are limited to the device's maximum texture size (`GpuError::TooLarge`); tiling larger outputs is still open (spec row "Output size not capped by the GPU").

**D27 (2026-10-18): The desktop shell is egui/eframe 0.31 on the same wgpu 24 as the renderer, and the licence policy was applied to it.** `ui-egui` (L6) holds all drawing; `apps/inbetween` is a thin `eframe::run_native` wrapper. Because eframe's wgpu device is shared (`GpuContext::from_parts`), the GPU renderer draws a frame straight into a texture egui paints; with no GPU the CPU renderer feeds an ordinary egui texture. Consequences for `cargo deny`: (1) egui's bundled fonts are under OFL and the Ubuntu Font Licence, outside our list, so `default_fonts` is off and the app bundles Roboto (Apache-2.0, `ATTRIBUTION.md`). (2) `BSL-1.0` (Boost, permissive like MIT) was added to the allow-list; it comes from the clipboard crates. (3) AccessKit is enabled for test builds only: the headless test harness needs it, but on Linux it pulls an AT-SPI stack with a known `quick-xml` vulnerability, so the shipped app leaves accessibility out for now (revisit when that dependency is fixed). (4) `exclude-dev = true`, and transitive "unmaintained" notices no longer fail the check (`unmaintained = "workspace"`); known vulnerabilities in anything that ships still do. The workspace Rust version moved to 1.85.

**D28 (2026-10-18): The shell only draws and reads input; the project changes through commands.** Canvases return `Action`s (add, select, drag, delete) and the app turns each into an engine command: `dots.add`, `dots.move`, `dots.delete`. Menus are generated from the registry (`menu` paths, shortcuts, `enabled` and its reason as a tooltip), so a new command appears with no UI change. A command needing input opens a form generated from its parameter schema, with a native file dialog for `Path` parameters (`PathUse` and extensions in `ParamSpec`). Keys the shell owns itself: Delete (needs the selected index), Escape, Space, F, arrows. All view state (zoom, pan, link, mesh and number toggles, selection, frame, fps, playback) lives in one serde struct, `ViewState`, persisted by eframe.

**D29 (2026-10-18): Editing semantics.** `dots.add` puts the partner at the same spot on both images (the person then drags it on one). Two dots may never share a spot on one image (`dots.add` and `dots.move` refuse, naming the image), so an edit can never make a project the renderer rejects. Edit commands are flagged `edits: true`: the registry snapshots the project first, records an undo step on success and restores the snapshot on failure. History keeps 200 steps. `edit.beginGroup` / `edit.endGroup` merge everything between them into one step; the shell wraps each drag in a group, so one drag is one undo step. `Session::revision()` changes on every edit, undo, redo and open, and drives cache invalidation (preview, mesh, source textures); `is_dirty()` drives the title asterisk. `project.new` takes two image paths (absolute is fine in memory); `project.save` rewrites absolute image paths relative to the file being written.

**D30 (2026-10-18): Preview colour.** The GPU preview target is `Rgba8Unorm` holding the sRGB-encoded premultiplied values the working space already uses, exposed to egui through an `Rgba8UnormSrgb` view (egui decodes sRGB textures to linear when sampling and re-encodes on output). Using the plain view double-encoded the colours and looked washed out; the real-window screenshot showed it. The M8 UI works on sequence 0; the sequence list is M10.

**D31 (2026-10-18): Morph types are a per-frame "mix" recipe; hold frames are timing.** `Mix::for_type(type, t)` in `inbetween-morph` gives each frame two weights, a brightness for each image and a mode: `Add` (`w1*s1 + w2*s2`, premultiplied) or `Over` (Image 2 scaled by `w2`, laid over Image 1). Morph is `(1-t, t)`; Morph Hold is `Over` with `(1, t)` so Image 1 never fades and shows through where Image 2 is transparent; Warp 1 and Warp 2 use one image at weight 1; Fade Out 1 and Fade In 2 dim an image's colour by `1-t` and `t` (alpha kept), skip the warp, and ignore the dots; Direct is Image 1 until `t = 1`, then Image 2. A weight of zero means that image is never sampled, so a type that does not use Image 2 renders without one (Warp 1, Fade Out 1). CPU and GPU share the recipe; the GPU gets it as five uniforms and a mode. Hold frames live on the sequence (`hold_start`, `hold_end`, 0 to 999 each, total capped by `MAX_FRAMES`): `Sequence::frame_time(index)` is 0 through the start hold, rises evenly across the morph frames, then 1 through the end hold. The morph frame count keeps meaning "including t = 0 and t = 1", so holds only repeat those two frames. Everything that counts frames (renderers, `export.sequence`, the preview, playback) uses `total_frames()`. Old files without the hold fields load with 0. New commands: `sequence.morphType`, `sequence.fit`, `sequence.mesh`, and `sequence.length` gained `hold_start` and `hold_end`. `ParamSpec::one_of` restricts a string parameter to a fixed set. "Enter as seconds" and apply-to-all for `sequence.length` are not done.

**D32 (2026-10-19): Curves are time remappings with pinned ends.** A `Curve` (doc) is 2 to 64 points with strictly rising x, all inside 0..1, running through the points left to right. The first point is (0, 0) and the last (1, 1) and neither may move, so the morph invariants hold with any curve: frame 0 is Image 1 and the last frame is Image 2. The spec's "caricature" overshoot is for the track curve (P2), not these. Between points the curve is a cubic Hermite spline with harmonic-mean tangents (zero at turning points), so it never overshoots a segment; `linear` switches to straight segments. `eval` clamps its input and output and falls back to the identity on a malformed curve, so a hostile file cannot panic or produce NaN, and `Sequence::validate` rejects malformed curves anyway (a project file with one fails to open). A sequence has two: the **feature curve** remaps the colour dissolve (`Mix::for_type(type, feature(t))`) and the **shape curve** remaps how far the dots have moved (`lerp(first, second, shape(t))`). The planner applies them, so CPU and GPU and every export agree with no renderer change. The mesh policy still switches to Image 2's mesh only at t = 1. Commands: `curve.feature` and `curve.shape` take an `op` (add, move, remove, linear, reset, apply_all); with no `op` they report the curve. The spec's `curve.edit` gestures are those ops. Master and track curves and the curve library are still open.

**D33 (2026-10-19): Multi-sequence projects.** A project's visible sequences play one after another in list order (`Project::total_frames`, `Project::locate`); hidden ones are skipped. `Sequence::visible` is saved (old files default to visible). List commands live in `list_cmds.rs`: `sequence.addBlank`, `sequence.add` (continues the previous sequence: Image 1 is its Image 2, frames, type, fit and mesh are inherited), `.delete`, `.duplicate`, `.rename`, `.visibility` (with `solo`, a toggle), `.reorder` (`move` or `to`), `.link` (a one-time copy of the previous Image 2 reference), `.copyFrame` (image plus its dots from one sequence into an image slot of another; the other side starts unmoved). `export.movie` writes every visible sequence as one continuously numbered series and `ib render` uses it unless `--sequence` is given (one sequence then renders as before). The shell keeps `ViewState::sequence`, the sequence the panels edit and the preview plays; `run_command` adds that as the `sequence` parameter to any command that takes one and was not given one, and the menu runs commands that need only `sequence` without a form. Changing the selected sequence clears the preview; list edits move the selection with them. Layer projects (`project.type.layer`) are P2 and not started.
